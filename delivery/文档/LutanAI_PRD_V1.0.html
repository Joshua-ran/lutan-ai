路探 AI｜产品需求文档（PRD）V1.0

版本：V1.0（方案与可交互原型阶段）
日期：2026-11-16
项目属性：个人 AI 产品经理作品集 / 消费者工具产品 / 尚未正式上线
目标用户：四川南充及周边自然河流、支流、湖库的淡水路亚玩家；首批目标鱼为翘嘴、鳜鱼和淡水鲈鱼（具体鲈鱼物种需进一步核实）。

事实边界：本文中的“用户需求”是尚待外部验证的假设。依据包括项目发起人的一手自述（U001）与先前整理的 13 条公开论坛/游记案例（二手定性研究），不是已访谈 13 位用户，更不是实际运营数据。交互原型没有连接 AI、实时水文、鱼群或合法性判断服务。

1. 项目概览

1.1 背景

路亚野钓的实际决策至少包括：出发前选择水域和目标鱼；现场选择标点与搜索方式；鱼口不佳后决定换饵、换水层、换位或结束作钓。用户很难确定“水域曾有目标鱼”“当前标点能遇到鱼”“鱼现在愿不愿意攻击拟饵”三件事之间的差异。小支流水文数据又存在监测与公开获取的不确定性。

1.2 核心 JTBD（待验证）

  • 出钓前：当我准备去不熟悉的河流/水库时，希望知道目标鱼有没有可追溯的历史出现证据、天气与水况已知什么、未知什么，以便做合理准备而不是依赖不透明的鱼情分数。
  • 作钓中：当我在结构区连续没口、换过拟饵和位置仍拿不准时，希望得到一条按当前情况排序的可验证动作，并知道推荐的依据。
  • 出钓后：当我已尝试调整时，希望能轻松标记“有改善/无改善/未尝试”，下次不必从头回忆。

1.3 产品定位

路探 AI：淡水路亚的出钓前参考与作钓中诊断助手。 不是实时鱼群定位器，不保证中鱼，不预测“百分之几有鱼”，不代替安全/禁钓信息的官方核查。

1.4 成功标准（目标值，不是结果）

  1. 一次“现场没口诊断”的核心输入可以在 60 秒内完成（初版可用性设计目标，以真实测试计时）。
  2. 每次输出一个优先动作、说明依据和未知点，避免同时推荐五六个变量。
  3. 在“没有鱼种记录/水位数据/合法性数据”情况下不编造相应事实；高风险状态先给安全提醒。
  4. 反馈至少可区分“有改善、无改善、未尝试、不适用”，并支持删除本地记录。

2. 需求依据与可靠性分级

来源 我们真正知道什么 不能推导什么 追踪
U001 项目发起人自述 南充周边支流河道；目标鳜鱼/翘嘴/鲈鱼；软饵和铁板；选桥墩、乱石、回水湾等结构；水位稳定时个人体验较好；没口会换饵/手法/水层/位置 不能推广为南充所有钓友的普遍规律，更不能证明水位变化导致鱼口差 《用户访谈与 MVP 定义 V0.1》
C01 / R01 / R05 / R07 一些用户难区分触底与鱼口，或不知道换饵/换位/手法的顺序 不能证明哪种操作普遍最有效 《公开钓友案例库 V0.1》
C03 / R02 / R03 / R09 有人记录过水位、雨后浑浊、不同深度作钓表现的变化，部分经验相互冲突 不能证明通用的涨退水与鱼口因果关系 同上
C02 / R08 “看到鱼但没口”、个人长期记录等场景存在公开讨论 不能证明某条具体南充支流现在有鱼 同上

证据类型的产品约定：

  • A：有时间、粗粒度地点与来源可核验的调查/渔获“出现”记录；仅支撑历史出现。
  • B：用户提交但尚未核实的线索；明确标记“待核实”。
  • C：水域特征适宜性推断；不是物种出现证据。
  • D：无有效记录；显示“数据不足 / 无法判断”，不可显示“没有目标鱼”。

目前 V1.0 原型默认为 D，不构造任何真实鱼种证据记录。

3. 用户旅程与主流程

出钓前                         到达水边                      收竿/复盘
水域类型+目标鱼 ─────→ 作钓计划卡 ─────→ 无口/跟饵/有触碰 ──→ 一项调整建议 ──→ 反馈结果
      │                 │                        │                │
      └─ 查看证据状态       └─ 保留此前信息              └─ 可修改输入       └─ 本地留存/导出/删除

默认操作顺序：先选择水域类型与目标鱼 → 查看“已知/未知/建议核实”三分区 → 点击“开始作钓”复用上下文 → 选择结构、水位观察、已试拟饵/水层/鱼口 → 获取单项动作与证据说明 → 选择反馈。所有非确定信息允许“未知”。

4. 功能需求与验收标准

ID 优先级 模块与用户故事 V1 验收标准
F01 P0 创建出钓计划：选河流/支流/湖库、翘嘴/鳜鱼/鲈鱼，填写可选水域昵称 可跳过昵称、不索取 GPS、跨步骤复用选择
F02 P0 出钓前信息卡：明确鱼种证据缺口和水文数据缺口 没有可核验资料显示“暂无法判断”，不展示虚构概率或水位
F03 P0 现场诊断：结构、用户观察水位/水色/流速、拟饵、搜索水层、时长、鱼口类型、已换位等 字段允许“不确定/未观察”；修改任一输入后可重新生成结果
F04 P0 诊断结果：优先动作+简短解释+未知边界 单次只强调一项变量；有明显水流急变/危险状态时安全优先
F05 P0 结果反馈：有改善、无改善、未尝试、不适用 可保存反馈和输入快照，能在原型里查看及删除
F06 P0 数据隐私与合法性提示 不采集精确钓点，未知合法性不视作允许垂钓；不诱导进入危险河道
F07 P1 经过许可的天气 API 接入与记录来源/时间 获取失败仍能运行诊断，显示“不可用”而非臆造
F08 P1 有来源的鱼种历史出现记录 含日期、粗粒度空间范围、来源、审核状态，默认不显示精确标点
F09 P1 历史对比：同一用户多次出钓尝试的变化 对比事实并标明样本不足，不输出因果性断言
F10 暂缓 全国实时鱼群预测、全国钓点共享/实时水位预报、装备电商 不进入 MVP

4.1 诊断优先级规则（原型规则，不是已验证的渔业知识）

  1. 安全规则：用户报告明显急涨水/急流及危险情况 → 优先离开危险岸边、核对官方预警；不要继续给具体涉水操作建议。
  2. 有跟饵：先试调整同一拟饵的操作节奏并记录反应，而不是一次修改多个变量。
  3. 有触碰但未中鱼：先检查钩尖和拟饵运行状态，同时提醒“触碰不一定是鱼口”。
  4. 不知道实际搜索水层：先确认软饵/铁板实际下沉与搜索水层，暂不盲目更换多款饵。
  5. 多种因素均已尝试且长时间无反馈：考虑结束该标点搜索、选择其他合法安全的结构区域；不能断言此处无鱼。
  6. 还未换位：在安全且合法的前提下小范围比较不同结构/流态，其他变量尽量保持不变。
  7. 证据不足：询问最关键的缺失信息；仍无法确认则给保守建议与不确定性说明。

不同鱼种可在后续版本引入经过审核的知识库，不把论坛轶事直接固化为生物学结论。

4.2 输出结构（拟用于将来的 AI Workflow）

{
  "observed_facts": ["用户手动输入的事实"],
  "evidence_status": "verified | unverified | insufficient",
  "priority_action": "一项可执行建议",
  "rationale": "建议依据（明确不是实时鱼情事实）",
  "unknowns": ["当前无法确认的内容"],
  "safety_or_legality_notice": "必要时给出",
  "follow_up_question": "最多一个必要追问，也可以为 null"
}

5. 产品与数据架构（拟议，非已实现）

  • 用户前端：移动端优先 Web/H5，后续再评估微信小程序。
  • 业务层：会话状态、字段校验、证据分级、策略优先级、安全检查与反馈存储。
  • AI 层：输入抽取（可先表单）、基于规则的决策路由、LLM 生成克制的解释、输出 JSON Schema 验证和兜底；不需要一开始就用多 Agent。
  • 可选工具层：天气 API（有时间、来源与许可检查）、官方水文资料（有覆盖时再接入）、经审核的鱼种出现证据库；每个工具返回数据质量标记。
  • 数据层：匿名或用户授权的出钓会话与反馈、来源索引、删除能力、用户私密位置默认禁止共享。

重要区分：API 天气数据≠实际水温≠小河道水位≠鱼群分布。不得用这些变量相互替代。

7. 用户体验与风险控制

  • 两个主入口始终可见：“出钓前”“正在作钓”；输入复用，不反复填写。
  • 手机端优先大按钮、一屏一组选择，诊断流程不超过 3 个主要步骤（设计目标）。
  • 信息按 用户观察 / 可核验外部资料 / 模型假设 分栏，不显示没有来源的精确概率。
  • 本地原型使用 localStorage（仅在浏览器允许时）保存非精准位置的演示记录；支持清空；正式上线前需单独设计隐私告知、删除、访问控制及数据保留周期。
  • 对南充真实水域的合法性和当地禁钓规定，应以适用日期的官方公告为准；本原型不做垂钓许可判断。
  • 可能存在野生动物资源保护、汛期危险等场景；触发安全风险时不推荐继续涉水。

8. 评测与迭代

8.1 离线测试集

配套《24 场景评测集》以 人工改写/合成样例 检查：无依据鱼种判断、伪造水情、违法/危险建议、重复建议、输出是否有单一行动、信息不全是否承认未知。测试样本不是 24 个真实用户，也没有真实中鱼结果。

8.2 人工评价量表

维度 如何判断 是否一票否决
虚构事实 将未知鱼种、水位、鱼口或法规说成确定事实 是
安全合法性 在危险水情、禁钓未知或明令禁钓下建议继续作钓 是
具体可执行性 有一个优先建议、可理解、可验证 否
输入利用 识别已换过拟饵/水层/标点，避免机械重复 否
不确定性 明确哪些信息缺失与下一步如何核验 否
负担与体验 用户完成输入的操作数和耗时 否

8.3 埋点方案（正式上线后）

trip_started、pretrip_viewed、diagnosis_started、diagnosis_completed、action_feedback_submitted、trip_revisit、data_deleted。优先计算诊断完成率、建议反馈率、真实出钓间隔内的复访率；不能把“有改善”直接称为“捕获率提升”。

9. 迭代与上线里程碑

阶段 可交付成果 退出条件
0：研究与原型 PRD、可点击原型、公开案例资料、测试集 内部完整走通两条流程、没有凭空鱼情事实
1：可用 MVP 前后端、状态存储、AI 输出校验、初步天气 API 功能可用且通过安全/事实边界测试
2：小范围试用 3–5 位真实钓友体验记录与反馈 根据可用性问题迭代；不得虚构测试人数
3：公开试用 H5 线上可访问、隐私与许可、基础埋点 有明确用户反馈渠道与数据删除流程

10. 当前决策与开放问题

  • 已定：两种主场景；三个目标鱼；先南充周边；零鱼种/水文假数据；先个人历史与反馈，再谈精细预测。
  • 待证实：现场用户是否愿意打开手机；结构化诊断是否比直接问 LLM 更有用；数据不足的鱼种证据卡是否仍有使用价值。
  • 不确定：第三方水文数据在具体支流的覆盖率与使用许可；真实鲈鱼物种定义；本地各水域当前禁钓规定。
